# Mandant als Job-Attribut, dedizierte Queues nur für Rate-Limits

Jobs tragen optional einen **Mandanten** (`tenant`, z.B. `wachmacherei`) als Attribut neben Consumer und Credential-Referenz — Queues werden weiterhin nach Job-Art geschnitten (ADR-0003), nie nach Kunde. Die Frage "welches Google-Konto?" beantwortet die Credential-Referenz (ADR-0002), die Frage "zeig mir alle Jobs von Kunde X" das Job-Archiv in Postgres (filterbar nach Mandant, Consumer, Typ, Status, Zeitraum) — Bull Board bleibt reines Ops-Werkzeug und kann nicht nach Payload-Feldern filtern. Einzige dokumentierte Ausnahme für dedizierte Queues: ein externes Rate-Limit oder Fairness-Problem (z.B. Shopify Admin API limitiert pro Shop → `shopify-<shop>` mit BullMQ-Rate-Limit), denn BullMQ-Rate-Limiting wirkt pro Queue; dank queue-agnostischem Worker ist das eine Env-Var-Änderung, kein Umbau.
